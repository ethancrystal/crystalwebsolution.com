**Live check, first pass (WebFetch, no cache-bust):** `/about` and `/blog`
served the correct new titles; `/contact`, `/process`, and `/services` served

the bare URL — **MJ: worth a manual cache purge in Vercel for `/contact`,

**2. Login/signup indexing.** `app/robots.js` source confirms `/login` and
`/signup` are **not** in the disallow list (only the three role portals
`/login/admin`, `/login/client`, `/login/employee` are), with a comment
recording MJ's 2026-09-11 decision. `app/signup/layout.jsx` and
`app/login/layout.jsx` both declare `robots: { index: true, follow: true }`.
Live WebFetch of `/login` and `/signup` confirmed `index, follow` in the
page-level meta tag on both, first pass.

**But the first-pass live `robots.txt` fetch showed the OLD file** —
`Disallow: /login`, `Disallow: /login/`, `Disallow: /signup` still present,
which would stop a crawler reaching either page regardless of the page-level
meta tag. A cache-busted refetch returned the correct current file (only
`/login/admin`, `/login/client`, `/login/employee` disallowed, no `/login` or
`/signup` line). Same CDN-staleness conclusion as above, same recommendation:
purge `/robots.txt` specifically, since a robots.txt disallow is normally
respected for longer than a single crawl and this one currently only clears
on a cache-busted request.

**Net:** both items are correctly fixed in code and at origin. Neither is
fully confirmed as correctly served to an anonymous crawler hitting the bare
production URL as of this run — **carrying this forward one more run** rather
than dropping it, specifically to re-check `robots.txt` and the three titles
on bare URLs (no cache-bust) once the CDN has had time to expire the stale
